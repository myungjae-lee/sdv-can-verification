# Day 5 - README 점검 및 CI 한계 확인

## 배경
README를 GitHub에서 확인해보니 실제 프로젝트 진행 상태(시나리오 5개 완료, 9개 테스트
통과)가 반영되지 않고 초기 상태(In Progress, 4 passed 등)로 남아있는 것을 발견.

## 한 일
1. `git log --oneline`으로 실제 커밋 이력을 확인해, README 내용과 실제 코드 상태가
   어긋나 있다는 것을 재확인 (README는 "미완료"라고 되어 있었지만 실제로는 시나리오
   2~5까지 이미 구현·커밋된 상태였음)
2. `pytest -v`를 로컬(WSL2 Ubuntu)에서 실행해 9개 테스트 전부 PASS 확인
   → 코드 자체에는 문제가 없다는 것을 검증
3. README를 현재 상태(완료된 시나리오, 테스트 개수, 구조, CI 설명)에 맞게 재작성

## CI가 vcan 테스트를 실행하지 못하는 이유

GitHub Actions는 `runs-on: ubuntu-latest` 설정에 따라, 코드를 실행할 때마다 새 우분투
**컨테이너**(격리된 임시 리눅스 환경)를 하나 띄웠다가 실행이 끝나면 버리는 방식으로 동작함.

`vcan0` 같은 가상 CAN 인터페이스를 쓰려면 `sudo modprobe vcan` 명령으로 **리눅스 커널에
모듈을 로드**해야 함. 이건 일반 파이썬 패키지를 `pip install`이나 `import`로 가져오는 것과는
완전히 다른 층위의 작업 — 커널 모듈 로드는 운영체제 심장부를 건드리는 것이라 별도의
관리자급 권한이 필요함.

컨테이너는 호스트(실제 물리 서버)의 커널을 여러 컨테이너가 나눠 쓰는 구조라서, 컨테이너
하나가 마음대로 커널에 손댈 수 없음. GitHub이 제공하는 공용 컨테이너는 보안 정책상 이
권한을 아예 막아두었기 때문에, **모듈이 없어서가 아니라 모듈을 로드할 권한 자체가 없어서**
vcan을 쓸 수 없었던 것.

→ 그래서 CI는 실제 CAN 통신 테스트(`pytest -v`)를 돌리는 대신 다음 두 가지만 수행하도록
구성함:
- `py_compile`로 문법 오류 체크
- `pytest --collect-only`로 import/수집 단계 오류 체크

실제 테스트 실행 및 검증은 vcan을 지원하는 로컬 리눅스 환경(WSL2 Ubuntu)에서 수행.

(참고: `sudo` 권한이 있는 self-hosted runner를 쓰거나 Docker를 `--privileged` 모드로
띄우면 컨테이너에서도 커널 모듈 로드가 가능하지만, GitHub 공용 러너에서는 보안상 지원 안
됨. 지금 프로젝트 규모에서는 필요 없는 방법이라 적용하지 않음.)

## 배운 점
- README 같은 문서는 코드가 바뀔 때마다 같이 업데이트하지 않으면 쉽게 실제 상태와
  어긋난다는 것을 직접 겪음 → 앞으로는 기능 단위 커밋 시 README도 같이 확인하는
  습관이 필요
- CI(클라우드)와 로컬(개발 환경)이 항상 같은 걸 검증할 수 있는 게 아니라는 것을 확인.
  하드웨어/커널 의존적인 기능은 범용 클라우드 CI에서 한계가 있고, 이런 경우
  "CI는 최소한의 안전망(문법/구조 체크), 실제 검증은 로컬/전용 환경"으로 역할을
  나누는 것이 현실적인 설계라는 것을 이해함
